**Codebase maintainability, generalizability, performance, and refresh analysis — October 22, 2026**

This is the pre-repair audit. See the [implementation and verification notes](../Runtime/implementation.md) for the subsequent repairs.

The main problems are inconsistent ownership of cached state, startup dependencies that are much larger than the visible screen, and success/failure distinctions that disappear between layers. These explain the reported empty initial screen and cases where reopening appears to fix stale data. The project already has useful foundations: static Astro output, shared aggregation helpers, content hashes, worker downloads, incremental shards, and explicit animation controllers. A framework rewrite is unnecessary; the data lifecycle needs a clearer contract.

This review covers the application, build and ingestion scripts, persistence, generated service worker, deployment workflow, and benchmarks at commit `10c5dcf`. Application source was not changed. Findings labeled **reproduced** were exercised locally; **source-confirmed** follows directly from the implementation; **risk** identifies a plausible failure that still needs targeted device testing.

Validation included `astro check` (97 files, zero errors, zero warnings, nine hints), a fresh static Astro build, the existing album-ranking assertions, isolated browser reproductions, an ingestion fixture, data benchmarks, and all eight existing browser benchmark scenarios. The full network-dependent enrichment build was not run. Browser checks used headless Microsoft Edge 155 with a 393 × 852 touch viewport, rather than a physical iPhone. The controlled startup/refresh checks disabled service workers to isolate application behavior and stubbed external images. Service-worker lifecycle findings are therefore source analysis, not an iOS reproduction. The fresh JavaScript bundles matched the existing `dist` bundles byte for byte.

The public data endpoint returned HTTP 403 from this environment, so deployed data freshness could not be verified. Local generated data is not evidence of the current production state.

**How data currently reaches the screen.** A daily GitHub workflow fetches Last.fm data into CSV, rebuilds the derived JSON, enriches metadata and media, generates a manifest, and deploys static files. In the browser, separate component scripts start on DOM readiness while the page boot routine establishes a generation. Reads pass through an in-memory map, IndexedDB, a worker, network fetches, and potentially service-worker caches. Above that layer, `ui.ts`, `scrobbles.ts`, and components hold additional caches and derived state.

The intended atomic generation is consequently spread across several independent mechanisms. A manifest pointer change does not itself guarantee that all objects, derived views, and pending requests now belong to that generation.

**1. P0 — Ingestion can remove recent history on an API error. Reproduced.**

[fetch-lastfm.js](/Users/aakash/Desktop/music-stats/scripts/fetch-lastfm.js:141) retries HTTP/network errors, but accepts a successful HTTP response containing an API error body. When `recenttracks` is absent, it logs a warning and breaks. It then removes existing records from the fourteen-day overlap and replaces them with the incomplete `newTracks` array at [the merge/write step](/Users/aakash/Desktop/music-stats/scripts/fetch-lastfm.js:217).

In an isolated fixture, HTTP 200 with `{error: 11, message: "Service Offline"}` reduced two historical rows to one and exited zero. No actual account data was touched. A failure on a later page has the same structural danger: partial pagination is accepted as a complete replacement. The workflow's row-count check only rejects a completely empty database, and [the upload step](/Users/aakash/Desktop/music-stats/.github/workflows/daily-sync.yml:110) can persist the damaged result.

Validate API errors, response shape, and complete pagination before replacing the overlap. Keep the original CSV intact until validation passes, write through a temporary file, and reject suspicious reductions unless explicitly expected. Use a fixed upper timestamp for a paginated snapshot. Restore failures should fail distinctly from a legitimately missing first-run dataset; the current `aws ... || echo` handling conflates them. Add workflow concurrency and versioned backups so overlapping push/manual/scheduled jobs cannot overwrite each other's canonical input.

**2. P1 — The initial document cannot display meaningful music content immediately. Reproduced.**

[Dashboard.astro](/Users/aakash/Desktop/music-stats/src/components/Dashboard.astro:27) emits dashes, and list/rail/chart hosts are populated in browser scripts. [Layout.astro](/Users/aakash/Desktop/music-stats/src/layouts/Layout.astro:355) dismisses the splash on DOM readiness or a 700 ms timer, independently of content readiness. [The page boot routine](/Users/aakash/Desktop/music-stats/src/pages/index.astro:187) also hides it before hydration. This exposes an empty application shell while data work continues. It is usually missing content rather than an entirely missing HTML document.

Recaps [awaits the artwork cache before reading its small index](/Users/aakash/Desktop/music-stats/src/components/Recaps.astro:258). Rankings [awaits artwork while loading metadata](/Users/aakash/Desktop/music-stats/src/components/Leaderboards.astro:830). Recents [awaits artwork before aggregating its list](/Users/aakash/Desktop/music-stats/src/components/MonthlyTopLists.astro:322). Statistics [waits for artwork and colors alongside core data](/Users/aakash/Desktop/music-stats/src/components/Statistics.astro:360). Text that could render from small summary files is therefore blocked by multi-megabyte decorative indexes.

With 1,200 ms of manifest latency and 200 ms per data request, one controlled run showed the splash hidden and all measured data hosts empty at 1.07 s; totals at 1.67 s; recap cards at 8.45 s. Two earlier runs produced approximately the same post-manifest delay. This is latency injection, not a simulated cellular bandwidth limit or a production measurement.

Render a compact build-time snapshot into the HTML, including text and small top lists. On return visits, publish a compact stored view snapshot before loading full datasets. Render text with artwork placeholders immediately. Then stage a complete validated update and publish it once. A persistent splash would conceal the delay rather than solve it.

**3. P1/P2 — The startup critical set is too broad, and downloads are duplicated. Measured.**

[CRITICAL_DATA_PATHS](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:61) includes all artwork and colors. These expand into 128 shards. [Initial seeding](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:357) downloads that broad set while components independently request some of the same datasets. The worker's four-download concurrency applies [within each request](/Users/aakash/Desktop/music-stats/src/utils/dataSync.worker.ts:104), while each incoming message starts another independent sync. There is no shared queue or hash-level in-flight deduplication across those requests.

The controlled slow startup made 207 data requests by the time the recap rail appeared; 72 distinct paths were requested more than once. The store's logical-path `inflight` map does not deduplicate seeding against worker dataset downloads. On warm startup, [hydration](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:183) settles the manifest before filling memory, allowing component reads to duplicate IndexedDB reads and merges too.

Use one generation-aware download scheduler with shared promises keyed by content hash. Separate visible-screen summaries from optional indexes. Sharding is useful for incremental transfers; it does not help first paint when every shard must still be loaded and merged.

**4. P1 — The five-second manifest escape path is invalid for sharded datasets. Reproduced.**

[awaitManifest](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:50) stops waiting after five seconds even though the initial manifest fetch has a ten-second timeout. Before the manifest arrives, `fetchAppJson('/data/artwork.json')` cannot recognize the path as a dataset and falls through to a direct fetch. The build intentionally removes that monolithic file.

Delaying the manifest six seconds reproduced 404s for `/data/artwork.json` and `/data/colors.json`. Basic totals could load, but image/color loading failed. Successfully downloading the generation later does not automatically repair all wrapper caches or rerender those views.

Keep dataset-path knowledge available independently of remote manifest discovery, or return an explicit retriable “manifest unavailable” state. Do not issue a known-invalid network fallback simply to unblock a promise. Embed the minimal boot manifest/snapshot or retry manifest discovery while retaining usable content.

**5. P1 — Transient failures become session-long caches. Source-confirmed.**

In [ui.ts](/Users/aakash/Desktop/music-stats/src/utils/ui.ts:53), an artwork failure is cached as `{}`. That object is truthy, so subsequent loads return it. [Colors](/Users/aakash/Desktop/music-stats/src/utils/ui.ts:490) behaves similarly, and [catalogPromise](/Users/aakash/Desktop/music-stats/src/utils/ui.ts:87) remains a settled promise after failure, preventing another attempt. A failed catalog can make every subsequent detail open fail until the document is recreated.

Represent `idle`, `loading`, `ready`, and `error` separately. Retain the last valid value, reset failed in-flight promises, and allow bounded retries on reconnect or explicit refresh. Failure must never be indistinguishable from a successfully loaded empty dataset.

**6. P1 — An old request can poison the new generation's memory. Reproduced.**

[fetchAppJson](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:203) keys pending work and memory by path, without capturing and validating a generation token before writing its result. [commitGeneration](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:311) moves the manifest but does not cancel or supersede older reads.

The reproduction started a generation-1 network read, committed generation 2, then released the old response. The active manifest was generation 2, but the old read returned `{slow: 1}` and all subsequent reads continued returning `{slow: 1}`. This is a direct explanation for a refresh that succeeds while the screen stays stale.

Capture an immutable generation/hash snapshot per read. Key work by generation and logical path, and reject or discard results from superseded generations. Construct the next memory snapshot before publishing it. The same rule should apply to secondary caches and derived view models.

**7. P1 — Persistence failure is reported as success. Reproduced.**

[idb.ts](/Users/aakash/Desktop/music-stats/src/utils/persist/idb.ts:109) resolves bulk writes even when the database is unavailable, the transaction aborts, or a put fails. Single writes also resolve on request success rather than waiting for the transaction commit. Worker callers expect rejection to identify a failed write, so their catch blocks cannot enforce the intended guarantee.

With IndexedDB unavailable, the reproduction refreshed from generation 1 to 2, received `changed = 1`, and wrote a boot hint with `complete: true`, while reads still returned the generation-1 value. `commitGeneration` skips a missing new stored body and leaves the old memory entry untouched.

Reject failed writes and resolve successful writes on transaction completion. Implement an explicit memory-only mode if persistence is unavailable, with the same generation-consistency guarantees. Store completeness must be verified rather than inferred from download success. The distinction between request success and committed transaction success is documented by [MDN's transaction completion reference](https://developer.mozilla.org/en-US/docs/Web/API/IDBTransaction/complete_event).

**8. P1 — Statistics refreshes its inputs without refreshing existing chart series. Reproduced.**

[updateChart](/Users/aakash/Desktop/music-stats/src/components/Statistics.astro:649) adds datasets only for labels not already present. It never replaces the data array for an existing year. Calling `chart.update()` redraws the old array.

A controlled update increased the cumulative total by 123: the expected last point was 7,258, but the existing chart remained at 7,135. The data-update event and component reload both occurred. In addition, [initializeCheckboxes](/Users/aakash/Desktop/music-stats/src/components/Statistics.astro:672) selects every year on each reload, losing user deselections when totals, artwork, or colors update.

Replace or reconcile every selected year's data on a generation change. Preserve selection and story position independently of data loading. Recoloring should not reset the year filter or rebuild unrelated state.

**9. P1 — Rankings retains old metadata and available-year information. Reproduced.**

[loadMeta](/Users/aakash/Desktop/music-stats/src/components/Leaderboards.astro:830) immediately returns its component-local `meta` after the first load. The update listener invalidates rollups but calls that same short-circuiting loader, and does not subscribe to metadata or artwork changes. `availableYears` is also only populated during that first metadata load.

A browser reproduction published updated track names through the normal shared-cache metadata event and then triggered a totals update. The visible ranking still showed the old names. Newly allocated IDs can be skipped because the old dictionary does not contain them; rebased positional IDs can be interpreted as a different entity. A year rollover can leave All Time's available-year information stale.

Remove component-local source-data caches, or key them by generation. Rebuild dependent rollups when metadata, year files, or relevant preferences change. Artwork changes need their own lightweight repaint rather than relying on a future full reload.

**10. P1 — Refresh feedback cannot distinguish failure, unchanged data, or work already in progress. Reproduced.**

[stageUpdate](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:275) returns zero for offline state, an existing stage, an unchanged manifest, failed downloads, and caught exceptions. [Manual refresh](/Users/aakash/Desktop/music-stats/src/utils/dataRefresh.ts:115) interprets zero as “Already up to date.” The reproduction returned zero both for a simulated network failure and for a second refresh while the first was still downloading.

Return a typed result such as `updated`, `unchanged`, `offline`, or `failed`. Concurrent callers should await the existing operation. Carry verification and persistence failures to the UI, preserve the last good content, and show the last successful refresh time.

**11. P1 — The refresh trigger policy leaves several recovery gaps. Source-confirmed.**

[dataRefresh.ts](/Users/aakash/Desktop/music-stats/src/utils/dataRefresh.ts:228) revalidates on visibility changes and provides pull-to-refresh only in standalone mode. There is no `online` recovery listener, `pageshow` handling for a restored document, or periodic foreground freshness check. An already-visible tab can remain unchanged through a daily deploy. A request that failed during offline startup is not automatically retried when connectivity returns.

The backend itself is scheduled [once daily at 02:00 UTC](/Users/aakash/Desktop/music-stats/.github/workflows/daily-sync.yml:7). Browser refresh only checks deployed files; it does not query Last.fm. New listening events therefore cannot become visible before a successful backend sync/deploy, regardless of how often a user pulls to refresh.

Define freshness requirements explicitly. Refresh on reconnect, resume/pageshow, explicit user action, and a modest foreground interval if needed. Debounce those triggers into one operation. Expose separate “listening through,” “last server sync,” and “last checked” timestamps.

**12. P1/P2 — Generation consistency and cache retirement have additional holes. Source-confirmed risks.**

[Stage update](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:294) ensures only changed files exist. It does not verify that all unchanged required files are still present after eviction or an incomplete earlier seed. Dirty paths come from new files; removed files/datasets do not explicitly invalidate old memory. The direct network fallback for a missing file [parses and caches without checking its manifest hash](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:239); the final shard fallback does the same. A deployment changing a stable URL can therefore mix an older manifest with newer bodies.

[Garbage collection](/Users/aakash/Desktop/music-stats/src/utils/persist/generations.ts:93) retains only one manifest's files. Another open tab, installed window, or backfill worker can still need or be staging other hashes. Tabs share IndexedDB but receive no cross-tab generation notification. These multi-client races were not device-tested.

Use immutable content-versioned download URLs, explicit schema/app versions, required-file completeness checks, and generation-aware garbage collection. Coordinate staging/commit across clients, notify other clients of publication, and retain a previous generation or active-reader leases before deleting blobs.

**13. P2 — One generation causes multiple independent rerenders, with incomplete async cancellation. Source-confirmed.**

The store publishes one generation event but then dispatches [a separate event per refreshed path](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:342). Statistics can run `loadData()` repeatedly for totals, stats, colors, and artwork. Recents can rerun for recent data and year files. Rankings clears all lists to an [“Aggregating plays...” state](/Users/aakash/Desktop/music-stats/src/components/Leaderboards.astro:1010) on every update, including search input, rather than leaving the current result visible.

Rankings has a useful `dataEpoch` guard; equivalent guards are missing from several other asynchronous loaders. Recents can complete older work after newer work. [RecapStory's open routine](/Users/aakash/Desktop/music-stats/src/components/RecapStory.astro:1670) has no request token across year fetches, so rapid year taps can display whichever request finishes last. [Detail switching](/Users/aakash/Desktop/music-stats/src/utils/overlayController.ts:290) checks the open token before one asynchronous transition, but does not recheck after its later waits before applying content.

Publish one immutable data snapshot per generation. Coalesce each affected view's recalculation and preserve visible content until the replacement is ready. Apply cancellation/version guards after every asynchronous boundary that can mutate shared UI.

**14. P2 — Recap and detail displays have separate refresh lifetimes. Source-confirmed.**

[RecapStory](/Users/aakash/Desktop/music-stats/src/components/RecapStory.astro:1541) keeps a year-keyed `recapCache` without invalidation when that year's recap changes. Reopening the story within the same document can still show the old object even if the shared store is current. The detail controller reads caches on open but does not update an already-open entity when catalog counts change. Neither behavior is communicated to the user.

Key story payloads by generation/hash, and define whether an open story/detail should refresh immediately or retain a stable snapshot until closed. In either policy, the next open should use the current generation. Catch story fetch failures and display a retry state; currently the event handler launches the promise without a user-visible error path.

**15. P2 — Infinite scrolling bounds insertion work, but not retained DOM or all cleanup. Source-confirmed.**

[createInfiniteScroll](/Users/aakash/Desktop/music-stats/src/utils/infiniteScroll.ts:71) appends every visited chunk and never removes distant rows. `content-visibility` reduces layout/paint, but DOM nodes, listeners, images, and application references still accumulate. The eventual cost grows with browsing depth and library size.

[MonthlyTopLists.renderAllLists](/Users/aakash/Desktop/music-stats/src/components/MonthlyTopLists.astro:271) deletes controller references without calling their `destroy()` method. Rankings performs that cleanup correctly; Recents does not. Detached sentinels and their observers can remain reachable across refreshes. Artwork retry/stall machinery also lacks a component-level cancellation hook, so discarded rows can continue through pending work.

Destroy controllers before replacement. Add a small bounded rendering window if deep browsing is common, and retain scroll position across refreshes. Scope artwork cancellation to the lifetime of the corresponding DOM/view.

**16. P2 — Significant main-thread work remains despite worker downloads. Measured/source-confirmed.**

Workers download, hash, and initially parse files, but [dataset reassembly](/Users/aakash/Desktop/music-stats/src/utils/dataStore.ts:136), structured-clone delivery from IndexedDB, aggregation, sorting, HTML construction, and DOM replacement still happen on the main thread. The local data benchmark measured artwork parse/merge at 9.1/10.7 ms and catalog parse/merge at 18/12 ms. Those are desktop Node measurements, not browser task measurements, but they show the amount of work repeated when whole datasets are reconstructed.

[All-time aggregation](/Users/aakash/Desktop/music-stats/src/utils/scrobbles.ts:139) scans selected daily history, then creates and sorts category arrays. Desktop renders three categories. [FLIP capture](/Users/aakash/Desktop/music-stats/src/utils/flip.ts:29) reads `offsetTop` across all retained rows, and the playback loop reads each row's layout position before filtering to the viewport. [Album cards](/Users/aakash/Desktop/music-stats/src/utils/overlayPopulate.ts:405) are built in one batch even though track lists are chunked. Two animation frames before expensive work do not make that work free or guarantee an unstuttered transition.

Prioritize profiling on a real lower-power device. Move full aggregation and materialization to a query worker or precompute compact summaries. Memoize by generation plus query parameters. Bound DOM size and batch layout reads separately from writes. Avoid moving every cosmetic operation into a worker before fixing the larger data dependencies.

**17. P2 — Background artwork work remains large and does not adapt to user/network conditions. Source-confirmed.**

[prefetchArtwork](/Users/aakash/Desktop/music-stats/src/utils/artworkPrefetch.ts:290) sweeps the full artwork URL list, uses six background requests at once, and can produce multiple sizes per image. Off-main encoding is a good optimization, but network, decode, cache I/O, and quota pressure remain. There is no Save-Data/connection-aware budget, hidden-page cancellation, or user-configured offline scope. Some thumbnail-size transformations differ between artwork sources, so a warmed source URL does not necessarily warm the actual thumbnail URL requested by the UI.

Artwork worker fetches and [main-thread sync fallback](/Users/aakash/Desktop/music-stats/src/utils/dataSyncClient.ts:80) lack the bounded fetch timeout used by the normal data worker. Both worker clients have pending maps without response deadlines. A worker that stalls without delivering an error can leave the current operation pending indefinitely. Hero preloading [waits for image load/error without a timeout](/Users/aakash/Desktop/music-stats/src/utils/overlayArtwork.ts:15).

Keep visible artwork first; make the rest a cancellable, budgeted offline task. Use one canonical source/size mapping for render and prefetch paths. Add per-request deadlines, worker liveness recovery, and explicit retry eligibility after transient hero failures. Cache API failures should not discard otherwise usable network responses.

**18. P2 — Service-worker lifecycle can produce mixed shell/module versions. Source-confirmed risk.**

[Installation](/Users/aakash/Desktop/music-stats/scripts/generate-sw.js:243) uses `Promise.allSettled` for shell assets and dependency crawling, then calls `skipWaiting`. [Activation](/Users/aakash/Desktop/music-stats/scripts/generate-sw.js:261) deletes older shell/data caches and claims active clients. A failed critical precache does not stop activation. A previously open document can still need its old lazy chart or worker bundle after its cache has been removed.

[Shell revalidation](/Users/aakash/Desktop/music-stats/scripts/generate-sw.js:159) can replace HTML in the existing shell cache without also ensuring the new HTML's dependency graph is cached. A later offline visit can therefore receive HTML whose modules are unavailable. There is no client `controllerchange`/app-version coordination. Immediate activation across existing clients is expected behavior of [skipWaiting and clients.claim](https://developer.mozilla.org/en-US/docs/Web/API/ServiceWorkerGlobalScope/skipWaiting), so compatibility has to be enforced by the application.

Also, [data response handling](/Users/aakash/Desktop/music-stats/scripts/generate-sw.js:87) awaits `cache.put` before returning the network response. Slow/failing cache writes can delay or reject an otherwise successful fetch. The manifest/fresh branch bypasses the three-second cache deadline, so that deadline does not cover the most important first-run reads.

Require critical shell assets before activating, keep prior assets while old clients exist, publish shell HTML together with its dependency list, and separate app-code updates from data-generation updates. Move opportunistic cache writes off the response-critical path and tolerate quota failures. Validate these cases in installed Safari, offline, across a real deployment.

**19. P2 — The custom chart has avoidable per-frame DOM work and GPU recovery gaps. Source-confirmed.**

[ReportsChart.paint](/Users/aakash/Desktop/music-stats/src/utils/reportsChart.ts:293) reads layout and rebuilds the y-axis HTML on every spring animation frame. Ticks generally do not need to change while bar heights animate. The renderer also requests a high-performance WebGL2 context for a small bar chart. There are no `webglcontextlost`/restored handlers; background/resume GPU loss could leave the chart blank. If WebGL acquisition succeeds but shader setup fails, falling back to 2D on that same canvas is not a dependable recovery path.

Cache geometry and axis markup until size/data scale changes. Either use the existing 2D renderer for this modest chart or explicitly handle WebGL loss and restoration. The repeated warm-sheet benchmark did not establish a persistent rendering freeze, so GPU/context loss remains a device-test hypothesis rather than a confirmed cause of the user's blank page.

**20. P2 — Zero is both a valid entity ID and an unresolved sentinel. Source-confirmed.**

The pipeline allocates arrays starting at zero, and the album-ranking test explicitly confirms album zero is valid. [events.ts](/Users/aakash/Desktop/music-stats/src/utils/events.ts:31) refuses ID `"0"`; [overlay clicks](/Users/aakash/Desktop/music-stats/src/utils/overlayPopulate.ts:435) also require a truthy ID. Statistics' album-to-artist builder skips album zero at [this conditional](/Users/aakash/Desktop/music-stats/src/components/Statistics.astro:376), and the detail payload has a similar artist-zero conditional. Some valid first entities cannot open or have missing attribution.

Use `null` or an explicit unresolved variant instead of zero. Validate numeric IDs with integer/range checks and allow zero. Track rows inside the detail overlay currently use placeholder ID zero, so preserving their intentional non-clickability requires an explicit flag or omitted entity ID.

**21. P2 — Calendar and time-window definitions are inconsistent. Source-confirmed.**

The processing pipeline groups by UTC date, reports use UTC, dashboard current-year selection uses local time, recap generation defaults to America/New_York, and Rankings combines local date arithmetic with UTC serialization. Some of this may be intentional, but there is no shared policy.

Statistics uses a 366-day leap-calendar axis with [a hardcoded 2024 tooltip date](/Users/aakash/Desktop/music-stats/src/components/Statistics.astro:490), while non-leap year's counts contain 365 entries without an inserted February 29 slot. Dates after February in those years are misaligned. Rankings subtracts seven days and uses inclusive date bounds, yielding up to eight calendar dates for “7d.” Recents similarly aggregates up to 29 dates for its 28-day subtraction, anchors to the latest scrobble rather than today, and labels that result “last 4 weeks.”

Adopt one explicit timezone and calendar-window convention, with clearly documented exceptions. Align every chart by actual month/day, and test leap years, year rollover, DST, midnight boundaries, and missing-data days. Decide whether Recents means a rolling interval through now or the last recorded listening period, and show that interval visibly.

**22. P2 — Enrichment order can leave playtime calculations one build behind. Source-confirmed.**

[build.js](/Users/aakash/Desktop/music-stats/scripts/build.js:21) processes the CSV before fetching new duration enrichment. [process-data.js](/Users/aakash/Desktop/music-stats/scripts/process-data.js:51) reads the previously cached durations when writing `meta.json`. Newly fetched durations then influence recaps but do not update those metadata tuples until the next build. This can make playtime Rankings and recaps disagree during the current deployment.

Separate dictionary extraction from duration enrichment and final materialization, or explicitly patch metadata/reprocess after enrichment. Require all published derived files to come from the same inputs and policy versions. The current pipeline also leaves old generated year/recap files in place when an input year disappears; a clean staging output directory avoids accidentally publishing obsolete artifacts.

**23. P2 — Data contracts, IDs, and configuration limit generalizability. Source-confirmed.**

The manifest has no runtime schema validation or schema-version handshake. Several catalog/stats payloads use `Record<string, unknown>` followed by assertions or `any`, so TypeScript cannot validate their actual relationships. Worker/build/client hash and merge conventions are duplicated. Entity IDs are positional and can shift after historical edits or changed grouping rules, so they are unsafe as long-lived identity without generation scoping.

The site URL, profile copy, recap timezone, minimum recap size, country-specific catalog search, date cutoffs, and browser target are spread across files. [The build targets Safari 18](/Users/aakash/Desktop/music-stats/astro.config.mjs:40), so broad compatibility needs an explicit supported-browser policy and matching test matrix. Statistics silently [filters out years before 2023](/Users/aakash/Desktop/music-stats/src/components/Statistics.astro:672). [Artwork loose matching](/Users/aakash/Desktop/music-stats/src/utils/artwork.ts:157) removes every non-ASCII letter; unrelated non-Latin album and artist names can collapse to the same empty normalized keys and receive the wrong cover. CSV writers escape embedded newlines, but all readers split into lines before parsing, so those valid CSV fields do not round-trip.

Create typed shared contracts for manifests, catalog buckets, recap payloads, and event results; validate at network/storage boundaries. Keep stable source identity or explicitly generation-scope positional IDs. Centralize profile, date, provider, and supported-browser policies. Use Unicode-aware normalization and a CSV parser that supports complete records.

The intended artist-overrides exception in [.gitignore](/Users/aakash/Desktop/music-stats/.gitignore:29) sits beneath an ignored parent directory, and `git ls-files src/data` is empty. Curated overrides are neither tracked here nor uploaded by the workflow. A clean checkout can therefore lose manual attribution corrections. Store durable overrides separately from generated/private data, and ensure bootstrap suggestions do not overwrite curated aliases.

**24. P2/P3 — Maintainability would improve most through clearer ownership, not more abstractions.**

[ui.ts](/Users/aakash/Desktop/music-stats/src/utils/ui.ts:1) combines source-data caching, artwork resolution, image retries, HTML construction, color lookup, and DOM styling. Large Astro components mix markup, styling, data acquisition, derivation, and controller state; file length alone is not a defect, but the hidden cache dependencies make changes difficult to reason about. Most components initialize on raw `DOMContentLoaded`, while a shared `onReady` helper already exists. Global DOM events have string names and no unsubscribe return, and generated service-worker code lives inside a large string rather than a separately checkable worker source.

Prefer a small set of explicit modules: shared wire/domain schemas; a generation repository and download scheduler; pure queries/derived models; view controllers with lifetimes; reusable renderers; and centralized configuration. Move data ownership out of presentation helpers. Preserve the useful existing decomposition for gestures, motion, and artwork lookup. Avoid abstracting every small function or migrating to a framework solely to address these bugs.

Accessibility is also part of UI health. Generated clickable rows and entity spans are not keyboard controls. Modal markup lacks focus trapping/restoration and background inertness. Navigation state is primarily a CSS class rather than complete selected-state semantics. [The viewport](/Users/aakash/Desktop/music-stats/src/layouts/Layout.astro:57) disables zoom. Use semantic links/buttons, consistent focus handling, chart text summaries, and accessible loading/error states. Existing Escape support and dialog labels are useful but incomplete.

**Performance evidence and its limits.** The full one-pass browser suite measured headline-stat readiness at 145 ms cold and 110 ms warm on localhost. That benchmark does not wait for the recap rail or all first-screen content, so those numbers can coexist with the eight-second slow-network reproduction. One initial sheet-open run recorded a 200 ms maximum frame and 428 ms of long tasks; a three-run warm-sheet repeat recorded a median 16.8 ms maximum frame, no stalls, and 66 ms to first movement. The repeat does not support a claim that the sheet reliably freezes.

The suite reported several baseline regressions, but the baseline's roughly 6.7 ms frame cadence differs from this run's roughly 16.7 ms cadence. A different browser/runtime/refresh rate makes many relative frame comparisons inconclusive. The outlier deserves real-device profiling; it should not be presented as a proven production regression.

The benchmark infrastructure itself has correctness gaps:

- [run.js](/Users/aakash/Desktop/music-stats/bench/run.js:224) catches a scenario error, skips it, and can still exit zero with “No regressions.” Missing or failed scenarios must fail the run.
- [metrics.js](/Users/aakash/Desktop/music-stats/bench/metrics.js:17) starts a new animation loop and observer without cancelling prior ones. An initial recorder and a later `record()` can leave multiple loops/observers running; old observers can inflate task counts and change overhead.
- Gesture descriptions overstate coverage: the tab scenario clicks buttons, and dismiss uses mouse dragging. These do not fully exercise iOS touch dispatch, gesture cancellation, or installed-PWA lifecycle.
- Tiny image stubs test network dependencies, but do not reproduce real image decode, resize, GPU, or cache-quota costs.
- Coverage is missing for slow manifest resolution, partial shard failure, offline-to-online recovery, successful generation replacement, quota failure, killed workers, multi-tab publication, deployment while open, and year rollover.
- The deployment workflow runs artifact shape checks, but not `astro check`, album-ranking assertions, or the browser suite. There is no standard test/lint command or top-level setup/architecture README. The live artwork “test” prints unsuccessful matches and still exits zero; it is a diagnostic, not an assertion suite.

Add focused integration tests for the reproduced failures before broadening cosmetic tests. Record useful-content readiness, total request/byte count, update completion, and actual visible state. Use physical Safari tests for resume, offline deploy changes, and memory pressure. Make performance budgets device/browser/refresh-rate aware.

**A practical repair sequence.**

1. Protect ingestion first: reject API error bodies/incomplete pagination, preserve the existing CSV, and add upload safeguards/backups.
2. Repair generation semantics: generation-scoped reads, typed refresh results, shared staging promises, truthful persistence errors, and a supported memory-only fallback.
3. Fix the immediate screen bugs: chart-series replacement, Rankings metadata invalidation, recap cache invalidation, valid zero IDs, and retries after reconnect.
4. Establish an immediate-content path: build-rendered or compact stored view snapshots; remove artwork/colors from text readiness; deduplicate downloads; publish one generation update per view while preserving selections and scroll.
5. Harden offline/app updates: complete shell precaching, compatibility/version handling, safe old-cache retirement, and real Safari lifecycle checks.
6. Profile and simplify hot paths: bounded lists, observer disposal, chart axis/geometry caching, generation-keyed queries, and worker aggregation where traces justify it.
7. Consolidate schemas/configuration, date policies, durable overrides, accessibility, CI checks, and architecture documentation.

For the desired behavior—content immediately, followed by one refresh—the acceptance criteria should be observable: first-load HTML already has useful text; warm offline launches show a compact cached view without network; a failed refresh preserves it and reports failure; reconnect retries; a completed generation updates all dependent views consistently once; and no prior request can overwrite that published generation.
